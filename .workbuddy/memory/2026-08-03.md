## v42.32 — 紧急 hotfix：修复 windowed exe 启动崩溃 (sys.stderr is None)
- 现象：双击 v42.31 exe 立即崩溃，栈顶 run_pyside6.py:77 `faulthandler.enable()` 抛 `RuntimeError: sys.stderr is None`。
- 根因：`--windowed`（无控制台）打包下 PyInstaller 把 sys.stderr/sys.stdout 置为 None，faulthandler.enable() 默认写 sys.stderr → 启动即崩。
  这是历史遗留（v42.30/v42.31 同一份启动文件 run_pyside6.py），只因本次首次真正双击 exe 才暴露（此前用户只看代码/源码跑，未双击 exe）。
- 修复（commit affc911，2026-08-03 17:18 推送 main）：run_pyside6.py 在 faulthandler.enable() 前检测 `sys.stderr is None`，则把 sys.stderr/stdout 重定向到项目根 `zpp011_stderr.log`（"w" 行缓冲）再 enable；global_exception_hook 文案改指日志文件。纯防御性、不碰业务逻辑；源码模式（有控制台）行为不变。
- 验证：模拟 `sys.stderr=None` 下 `import run_pyside6` 成功、sys.stderr 已重定向为文件对象（TextIOWrapper）。py_compile 通过；pyflakes 仅历史 F401 无 F821。
- 教训（写入 MEMORY.md）：所有 `--windowed` 打包入口若顶层调用 `faulthandler.enable()` / `print` / `traceback`，必须处理 `sys.stderr is None`；重定向到日志文件是标准做法。

## v42.33 — 修复未读概览与变动提醒看板数据不一致（用户截图指出「概览=1 看板=0」）

### 现象
用户截图显示：未读概览弹窗「变动提醒：1 条未读」，但点开变动提醒看板却弹「暂无已审核记录变动」（0 条）。两处对"变动提醒未读"用了不同口径。

### 根因
- 未读概览 `_count_unread_items`（main_window.py:2249）按主表 df 列 `_post_audit_changed==1 & _read==0` 算 N 条（加载时确定性写入，不依赖 DB）。
- 变动提醒看板 `_show_audit_changes_dialog` → `DataService.get_audit_changes`（data_service.py:261）在 mask 之外**额外 `load_read_status` 查 DB 历史基线 + 二次重比对**，
  `if not status_map: return []`（278）与 `has_baseline` 二次比对（297-298）在缺基线/重比对相等时把应展示的变动行**归零** → 弹「暂无变动」。
- 已实测排除 data_id int/str 查不到主键（SQLite 列亲和性让 int 命中 str 主键），确认是**口径不一致**而非查询 bug。

### 修复（commit 98ba371，2026-08-03 17:53 推送 main）
- `get_audit_changes` 重写为**以主表 `_post_audit_changed` 列为唯一真相**（与未读概览同源）：不再二次重比对归零；
  old 取 DB 基线快照（_hist_snap/_hist_note）、new 取当前主表值，缺基线也照常列出该行。行数 = 概览 count，完全一致。
- 顺带修两个真实炸弹（data_id 为 int 的真实数据上原会直接崩）：
  1. join 时 `sub['data_id']`(int64) vs `status_df.index`(str) 类型不匹配 → `ValueError`：统一 `sub['data_id'] = sub['data_id'].astype(str)`。
  2. join 时列名重叠（_hist_* 列已存在于 sub）→ `columns overlap`：join 前 drop sub 同名基线列。
- field 判定改「实际数量优先」（一行只返 1 条，与未读概览行级口径对齐）；备注原因仅在基线非空且真不同才记。

### 教训（写入 MEMORY.md）
- **凡是两个 UI 都用同一概念的"计数/列表"，必须共用同一数据源/列**，绝不能一个用 df 列、另一个二次查 DB 重算——边界情况下必脱钩。新增此类"双展示"时先确认口径统一。
